<h3>01 &nbsp;·&nbsp; 关于我</h3>

写后端第 7 年。做过单机撑不住就加机器的系统，也做过加机器也撑不住的系统 —— 区别通常不在代码，在于有没有人愿意先把瓶颈量出来。

现在专注三件事：**高并发下的数据一致性**、**微服务边界的治理**、**云原生环境里的可观测性**。喜欢能跑五年的简单方案，胜过只能跑五个月的精妙方案。

```yaml
engineer:
  name: LonggerKing
  role: Backend Engineer
  base: Guilin, CN
  focus:
    - high-throughput distributed systems
    - microservice governance & service mesh
    - cloud-native infrastructure
  currently:
    - shaving p99 latency off a Kafka ingestion pipeline
    - re-reading "Designing Data-Intensive Applications"
  principles:
    - measure before optimizing
    - boring technology, sharp edges
    - make the failure mode obvious
```

- 每周写一篇后端笔记，不追热点，只写踩过的坑

<details>
<summary><sub><b>工作方式 · 几条自我约束</b></sub></summary>


<br />

1. **先测量，再优化。** 没有火焰图和慢查询日志的「性能优化」都是猜测。
2. **让失败模式显式。** 每个 RPC 都要回答：超时了怎么办、重试几次、幂等吗。
3. **复杂度是负债。** 引入一个中间件之前，先证明现有方案真的不够。
4. **文档写给三个月后的自己。** 那时候你已经忘了为什么这么写。

</details>
